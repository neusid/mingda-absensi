# Taste
- Prefers UI/layout work to be hardcoded only (plain Flutter widgets) — the assistant should implement the visual layout and leave state management, navigation, and other logic to the user (e.g., builds pages with dummy data and notes "tinggal kamu sambungkan ke API nanti"). Confidence: 0.95
- Wants blocking bugs fixed before continuing with other planned work (e.g., asked to fix the endless-loading issue first, before resuming the Figma layout task). Confidence: 0.5
- When converting Figma designs to code, prefers to provide the Figma link together with the specific screen and layer info (e.g., layer name "00 Profile") so the assistant builds exactly that. Confidence: 0.95
- Is willing to share a Figma Personal Access Token so the assistant can read designs directly via the Figma REST API (node structure JSON + rendered PNGs), rather than relying on screenshots or MCP setup. Confidence: 0.8
- Delegates debugging/fixing of app bugs to the assistant — reports the symptom (e.g., "loading terus", pasted device logs showing failure states) and expects the assistant to investigate root cause, iterate, and fix it. Confidence: 0.95
- Shares raw runtime logs (flutter/device debug output, e.g., "Exception caught by gesture" tracebacks) when reporting a bug, so the assistant can diagnose from actual responses and state transitions. Confidence: 0.95
- Prefers new screens to be wired into the app's existing tab-based navigation structure (e.g., put the feature under its designated tab like "cuti") rather than registering standalone global routes that bypass the tab view. Confidence: 0.6
- When tab labels change to reflect what a screen actually is, expects the bottom-nav labels to be updated to match (e.g., renamed "Absensi"/"Izin" to "Cuti"/"Peringatan" when swapping screen contents) so the UI stays consistent. Confidence: 0.6
- Wants real content to actually display (e.g., the profile image) even when the source has server-side SSL/certificate issues — prefers a working in-app workaround (scoped to the problem host) over settling for a placeholder/fallback. Confidence: 0.6
- Works through the Figma design screen by screen — asks for one frame at a time by its frame name (e.g., "00 Profile", then "06 Work Leave", "08 Warning Letter") with terse instructions, expecting the assistant to autonomously run the whole established workflow (locate node, render frame, implement the page with design-faithful hardcoded UI, wire up navigation, verify with analyze/tests) without step-by-step confirmation; even a one-word "iya" confirmation is enough for the assistant to execute the whole implied change. Confidence: 0.9
- Figma frames get superseded by newer versions over time (e.g., "00 Warning Letter" replaced by "08 Warning Letter"); when the user flags a design update, expects the assistant to re-fetch the latest file data via the API and rebuild the already-built screen to match the new design — not keep the old implementation or reuse stale cached node data. Confidence: 0.7
- Communicates in Indonesian (Bahasa Indonesia); prefers replies in Indonesian. Confidence: 0.9
- Likes to verify things himself — asks for the raw API JSON/link (e.g., profile image URL) to check directly, not just the assistant's summary. Confidence: 0.5
- When the user defers a change with something like "tapi nanti" (but later), the assistant should acknowledge and hold off — not implement until the user explicitly confirms (e.g., tab/feature mapping corrections were noted but deliberately not applied, then implemented only after a terse "iya"). Confidence: 0.75
- Prefers skeleton/shimmer loading placeholders that mirror the actual screen layout over circular spinners — requested skeleton loading be added on every widget/page where a loading state appears (and expects all `CircularProgressIndicator`s to be replaced, with a reusable shimmer widget in core/widgets). Confidence: 0.9
- After a bug is fixed, wants a clear post-fix explanation of the root cause and how it was resolved (e.g., explicitly asked "kasih tau aku ... apa penyebabnya dan bagaimana membereskannya" for the RenderFlex overflow) — not just a terse "done". Confidence: 0.9
- Requires Flutter state management and features to be built with clean architecture + BLoC (Bloc → UseCase → Repository → DataSource → Model, DI via GetIt); explicitly requested "pakai clean architecture dan bloc" when adding state management. Confidence: 0.9
- Prefers reusing an existing shared BLoC (provided at the root/tab level) over creating a separate feature-specific BLoC when the screens share the same data source — e.g., keeping Profile on the existing DashboardBloc rather than making a dedicated Profile bloc. Confidence: 0.7
- When requesting scroll/animation behavior changes (e.g., making a summary section scroll away and a filter bar become sticky via SliverPersistentHeader), explicitly wants the existing UI/visuals preserved — "jangan diubah ui cukup animasinya aja" (don't change the UI, only the animation). Confidence: 0.9
- Uses the responsive `.w` dimension convention (e.g., `10.w`, `205.w`, `45.w`, `121.w`) for all layout sizes in the Flutter codebase; requests spacing/sizing tweaks in these units (e.g., "tambahkan jarak 10.w pada atas dan bawah"), and expects the assistant to keep those extents consistent with the layout (e.g., matching header min/max extent to content height). Confidence: 0.8
